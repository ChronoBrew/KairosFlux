# 架构与语义总览

给要改这个仓库的贡献者看的地图：时态内核的键空间怎么长、`as_of` 到底承诺了
什么、指纹是怎么定义的、双时态语义准备怎么演进。这里不重复协议字节布局——
线格式/opcode 表/状态码见 [Kair-协议规范.md](Kair-协议规范.md)；这里只讲
"为什么这么设计"与"语义边界在哪"。

权威来源：本文档的每一条语义描述都对照 `internal/temporal/`、
`service/temporal_store.go` 与 [`docs/rfc/时态内核-M0-版本化与as-of.md`](rfc/时态内核-M0-版本化与as-of.md)
逐条核实；如果本文档与代码/RFC 出现分歧，以代码为准。

## 1. 时态键空间

一个逻辑记录在存储层展开成三类物理键：

```
逻辑键（业务不变，调用方看到的"key"）    order:1001
版本存储键（每次写入产生一条，永不删改）  order:1001:v0000000000000003
当前指针键（指向最新一条版本）          order:1001:current
```

- **版本号 `seq` 定宽 20 位十进制**：这不是排版偏好，是让 LSM 的字典序扫描
  天然等价于数值序——`ScanRaw(prefix, prefix+0xFF)` 不需要额外排序就能拿到
  按 `seq` 升序的版本序列。定宽不够（seq 超过 20 位）在当前系统规模下不是
  实际约束。
- **`:current` 只存指针，不存数据本体**：指针值是 `(seq, payload_hash)`，
  真正的 payload 仍在对应的版本键里。这让"最新值是什么"（`GET` 的语义）与
  "完整历史"（`LIST_VERSIONS`/`as_of` 的语义）共享同一份存储，不需要维护
  两份数据。
- **崩溃安全顺序**：写入永远先落版本键、再落指针键（两次独立的
  `KVStore.Write`，各自走标准的先 fsync WAL 再落 memtable）。指针只会指向
  已经落盘的版本；如果进程在两次写之间崩溃，指针还没更新，重启后看到的是
  "指针指向上一个版本"而不是"指针指向一个不存在的版本"——多出来的那个孤儿
  版本键可以被回收，但绝不会出现悬空指针。

## 2. 版本语义：写不覆盖

`PUT_VERSIONED(key, payload, source)` 的效果永远是"追加一条新版本"，不是
"覆盖旧值"。这是与 v1 `PUT` opcode 的根本区别，也是本文档反复强调的边界：

- v1 `PUT`（opcode `0x01`）行为一字不改——同一 key 的旧值不可逆地丢失，这是
  它从一开始就有的语义，版本化能力不改写它，只是新增四个 v2 opcode 提供另一
  条路径。
- 生产写入管道（QuantScout 等）已经全部走 v2 版本化写入；v1 `PUT` 的覆盖
  语义只对尚未升级的老客户端兼容路径成立——"现在还是覆盖"这句话只在这个
  范围内成立，不要拿它去描述版本化写入。
- `source` 是 M2 引入的操作元数据字段（"谁写的"），M0/M1 时期的旧客户端调用
  `PUT_VERSIONED` 时协议里没有这个字段，语义上是"未声明"，不是"声明了空
  字符串"——两者在审计查询里会被分开处理。

## 3. `as_of(t)` 契约

`AsOf(versions, as_of)` 的定义：返回该逻辑键下所有版本中，`write_ts <= as_of`
的版本里 `seq` 最大的那一条；同一写入时刻的多个版本（理论上不应出现，但
定义仍需覆盖这个边界）按 `seq` 决胜。

**核心承诺、也是唯一必须记住的一条**：`as_of(t)` 绝不返回写入时间晚于 `t`
的版本，即使那个版本此刻已经存在于存储里。这是"点时查询"（point-in-time
query）区别于"最终一致读"的地方——一个 Agent 在 `t` 时刻问过一次
`as_of(order:1001, t)`，无论之后这个 key 又被写了多少次，同一个 `t` 的
`as_of` 查询结果永远不变。[README 的 Quick Start](../README.md#quick-start)
里 `get-as-of` 返回 v2 而不是已经存在的 v3，就是这条承诺的最小可复现例子。

**当前的时间语义（M0/M1 阶段）是单时态的**：`write_ts` 既是"系统何时知道
这件事"（transaction time），也被直接当成"这件事何时生效"（valid time）
使用——两者没有区分。`contracts/quote.schema.json` 里 `pit_semantics` 字段
对这一点有显式声明："本类型不区分有效时间与写入时间"。这不是遗漏，是 M0
范围内的裁决：先把"写入即版本、查询即 as-of"的地基打好，双时态（valid
time 与 transaction time 分离，允许"迟到的数据回填一个过去生效的版本"）
是后续里程碑的范围，见第 5 节。

## 4. 指纹定义

`Fingerprint(entries)` 是对一组 `(LogicalKey, Seq, Payload)` 三元组的确定性
摘要：

1. 先按 `(LogicalKey, Seq)` 排序——指纹与输入给入的顺序无关，只与内容集合
   本身有关（不依赖调用方按什么顺序枚举出这些 entries）。
2. 每条记录在参与哈希前带上 payload 的长度前缀——避免"键的后缀"与"值的
   前缀"在字节流里边界不清导致的歧义（两条不同的记录理论上可能拼出同一段
   字节流，长度前缀消掉了这个歧义）。
3. 对拼接后的字节流做 sha256，取十六进制（64 个字符）。

`REPLAY_FINGERPRINT` 的两种用法，边界必须分清楚：

- **无界查询**（`as_of_nanos<=0`，M0 的原始形态）：枚举前缀下每个逻辑键的
  "重放出的最新版本"，与该键当前的 `:current` 指针逐一比对（`mismatchCount`
  就是这次比对给出的数字）。这是"数据没有静默漂移"的可执行验收——注入单
  字节漂移会让某个键的重放结果与 `:current` 不一致，`mismatchCount>0`。
- **区间/定点查询**（`as_of_nanos>0`，M2 引入）：只做"重放到某个时刻的状态
  是什么"，**不与 `:current` 做对账**——`:current` 是"现在"的指针，跟一个
  历史时刻的重放结果比较没有意义。CLI 在这种模式下会显式提示"区间查询：
  未做 :current 对账"，不会打印"不一致数=0"去误导调用方以为通过了对账。

`export-writes` 导出文件末尾的 `export_fingerprint`是另一个概念，不要跟
`REPLAY_FINGERPRINT` 的指纹混淆：前者是"这次导出的这份 JSONL 文件内容"的
完整性校验值（`(LogicalKey, Seq, Payload)` 集合的摘要，用于校验导出文件本身
没有被搬运/截断损坏),后者是"这个数据集当前/某时刻状态"的语义指纹。导出是
派生视图、可以随时重新生成，真相源永远是存储本身——这是刻意的设计选择，
不做第二条写入路径去维护导出文件的一致性。

## 5. 双时态演进路线

| 阶段 | 时间语义 | 状态 |
|---|---|---|
| M0 | 单时态：`write_ts` 同时充当 transaction time 与 valid time；`as_of(t)` 只按 `write_ts` 过滤 | 已实现 |
| M1 | 契约层显式声明这一现状（`time_semantics.kind`），并按声明的 time-kind 分派单调性校验（而不是猜 key 里有没有冒号）；不改变时间语义本身 | 已实现 |
| M2 | 操作元数据信封给每条版本记录加上 `write_ts`（服务端时钟）与 `source`；`LIST_WRITES` 提供"某键某时段被谁写了几次"的审计视角——这是审计维度的扩展，仍然不引入独立于 `write_ts` 的第二套时间轴 | 已实现，待合并 |
| M3 | 声明式 Job 控制面把"调度/重试/事件"本身也变成时态内核里的对象（`job:events:{name}:v{seq}` 走同一套版本语义）——是temporal 内核的一个消费方，不改变内核语义本身 | 任务书已定，未开工 |
| M4+ | 双时态查询（valid time 与 transaction time 分离，支持"迟到的回填"：`t_valid` 早于写入当时但写入动作发生在 `t_tx`）——目前只有方向,没有设计 | roadmap，无代码 |
