# 迭代复盘：两处数据竞争——最热路径上的无锁跳表遍历

日期：2026-08-13　范围：`storage`（`Engine.Get`）、`bannet`（`ConnManager`）

## 背景

新增 Go SDK 时写了一个「多 goroutine 共用一个 client、并发读写同一批 key」的用例，对**真实服务端**而非桩运行，并开 `-race`。它立刻炸出两处既有竞争。

## 竞争一：`Engine.Get` 无锁遍历跳表（每次 GET 都在其中）

```go
m.mu.RLock()
active := m.active   // 只在锁内拷贝了指针
m.mu.RUnlock()       // ← 锁在这里就放了
active.search(key)   // ← 无锁遍历链式结构，而 Put 正持写锁改写它的节点指针
```

后果不止竞态告警：读者可能跟到**只连了一半的新节点**，读出错值，甚至解引用空指针使进程崩溃。而它位于**每一次 GET 与 PUT** 的路径上。

**为何长期未被发现**：既有测试没有对同一实例并发做 Get+Put；压测走的是编译好的二进制、不开 race 检测——压多久都不会暴露。

**修法**：把 active 的查找收进锁内。**只圈内存查找、不圈 SSTable 查找**——后者要读磁盘，一并持锁会让写入停等 I/O；`dirty` 一经交换便不再被写入，故无需持锁。

顺带删除 `WriteSSTable`：它犯同一个错误（锁外全表遍历），且**零调用方**。不可达即删除，不修。

## 竞争二：`ConnManager.Len` 无锁读 map

`Add`/`Remove` 在锁内写这张 map，而 `acceptLoop` **每接受一个连接都调用 `Len`** 做 `MaxConn` 准入判断，二者天然并发。

无锁读 map 撞上并发写 map 时，Go 运行时会直接抛出 `concurrent map read and map write` **使进程崩溃**，而非仅报告竞态。此前无测试并发压 accept 路径。

## 验证

`go test -race ./...` 连跑 3 次稳定；SDK 并发用例中「响应串话」会表现为读到别的 key 的值，故它同时守护连接池的正确性。

## 教训

这两处都不是「写得不够优雅」，而是**并发正确性缺陷**，且都藏在既有测试的盲区里：一个缺「并发压同一实例」，一个缺「并发压 accept」。压测不开 `-race` 时，负载再大也只是把竞争窗口踩得更频繁而不会报错。
