# 迭代复盘：真分片（rf<节点数）+ P2C 转发读——让副本读 LB 有真实价值点

日期：2026-08-05　范围：`service/cluster`、`service/shardkv`

## 起点：一个会变成"空操作"的功能

计划里的下一步是「把 P2C 负载均衡接进 ShardKV 副本读」。动手前先自查：**当前拓扑下它有没有真实价值？**

结论——**没有**。彼时 `NewNode` 给每个节点都建了每个分片（全副本），发起读的节点**永远是该分片的副本**，本地读既最快又正确。P2C 要么正确地选本地（远程 RPC 成死代码），要么强制走远程（自我劣化），要么只有**注入人为延迟**才"看得出价值"。

而"想给某副本注入 `readDelay` 让它变慢来演示"这个念头本身就是危险信号：**一个只有靠人为故障注入才显示收益的功能，在真实负载里就是没收益**；配一个绿色的"分布测试"更会让它看起来有用，其实只是把凭空造的负载均衡掉了。这与本仓 measure-first、诚实标注的底线相悖。

根因一句话：**副本读 LB 只有当"调用方本身不是该分片的副本"时才有价值。** 当前拓扑没有这种调用方——所以要先把拓扑改真。

## 改真：分片只放置到副本子集（rf < 节点数）

`cluster.ShardReplicas(ring, shardID, rf)`：以分片锚点在一致性哈希环上顺时针取前 rf 个物理节点作为副本集。

- 走环而非取模，是为了让「分片 → 承载节点子集」与既有一致性哈希环统一：**各节点用同一环独立算出完全一致的副本集与顺序**，无需任何协调，Raft 组的 peers 顺序、每节点在组内的下标（`me`）在各副本上天然一致。
- `NewNode(addrs, me, shardCount, rf, dataDir)`：本节点只托管「自己属于其副本集」的分片，每个这样的分片建一个 Raft 组、peers 即副本子集、`me` 为组内下标。`rf >= 节点数`时退化为全副本（向后兼容，现有全副本测试传 `rf=N` 语义不变）。
- `rf < 节点数`即真正的**数据跨节点分区 + 每分片多副本**：3 节点 rf=2 时，每个分片只落在 3 选 2 的节点上。

## 价值点：P2C 转发读

有了非副本调用方，副本读 LB 才立得住。`Node.Get`：

- 本节点托管该分片 → 本地读（最快、无网络）。
- 否则 → 用 **P2C** 在该分片副本集间按「延迟 EWMA × 在途」择优，经**共享连接池**（`Raft.PooledCall`，与 RaftRPC 共用每对端那一条多路复用连接）转发到被选中的副本（`ShardRead.Get`）；RPC 失败顺序回退其余副本。

这正是之前建的 P2C 原语与连接池的真实归宿——两者在这条路径上同时发挥作用。

## 一个被测试暴露的认知修正

最初的分布测试**串行**连发转发读，断言"两个副本都被用到"，结果**失败**：80 次读全落在同一个副本。

这不是 bug，恰恰是 P2C 设计使然——**串行读时它会正确地收敛到最快副本**。是我的断言错了：P2C 的价值是延迟最优，不是平均分布。

修正后的诚实断言分两层：

1. **路由正确性（确定性）**：转发读只落在该分片副本集内，**绝不**落到非副本的调用方。
2. **负载均衡（并发场景）**：唯有**并发**负载下 inflight 项才让繁忙副本变得不划算、把读摊到其余副本——这正是"网关同时转发大量读"的真实场景，无需注入延迟。实测 8 goroutine × 40 读，两副本 157/163，均衡。

## 验证

`service/cluster` + `service/shardkv` 全绿、`-race` 干净、真分片端到端测试稳定 10/10。放置断言确认每分片恰好 rf 个副本、存在分片未被某节点托管（真分区而非全副本）。
