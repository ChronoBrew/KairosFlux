## 1. gnet（Go，事件循环模型）

**定位**：纯 Go 实现的高性能、轻量级、非阻塞事件循环网络库，直接做
epoll/kqueue 系统调用，不经标准库 `net` 包，工作方式类似 libuv/libevent。

### 1.1 连接生命周期：显式回调枚举，状态转换靠 Action 返回值驱动

gnet 的生命周期不是一个独立的"状态机对象"，而是**六个生命周期回调 + 一个
Action 枚举**的组合，这六个回调本身就是状态转换点：

```go
type EventHandler interface {
    OnBoot(eng Engine) (action Action)      // 引擎就绪，可以接受连接
    OnShutdown(eng Engine)                   // 引擎关闭，所有连接与事件循环已关闭后触发
    OnOpen(c Conn) (out []byte, action Action)  // 新连接建立
    OnClose(c Conn, err error) (action Action)  // 连接关闭，err 是"最后一次已知的连接错误"
    OnTraffic(c Conn) (action Action)        // 收到数据
    OnTick() (delay time.Duration, action Action) // 引擎启动后立即触发，此后按 delay 周期触发
}

const (
    None     Action = iota // 无动作
    Close                  // 关闭这个连接
    Shutdown               // 关闭整个引擎
)
```

每个回调的返回值 `Action` 直接决定下一步状态转换——`OnTraffic` 处理完数据后
返回 `Close` 就等价于"这个连接现在要进入关闭流程"，不需要另外调用一个独立的
"关闭"方法。`OnClose` 的 `err` 参数**统一承载**"是对端正常断开、异常断开、
还是本地主动关闭"这几种不同的关闭原因——不是分成几个不同回调，而是一个回调
+ 一个可能为 nil 的 error 参数区分。

**没有找到的信息**（标注不确定）：官方 Overview 页面没有给出 `OnOpen`→
`OnClose` 之间是否有更细粒度的中间状态（如半关闭），也没有描述连接超时是
通过什么机制触发 `OnClose`——大概率是靠用户在 `OnTick` 里自己实现超时检查，
但没有查到确认这一点的原文。

### 1.2 分层模型：事件循环 = 传输 + 分发，编解码留给用户

gnet 采用"多 reactor"架构：一个主 reactor 负责 `Accept`，多个 worker
reactor（每个绑定一个操作系统线程）分摊已建立连接的 I/O 事件。**没有独立的
编解码层**——`OnTraffic` 拿到的是原始字节缓冲区（`Conn` 实现了 Reader/Writer
接口），协议解析代码是用户在 `OnTraffic` 里自己写的，gnet 本身不提供帧
协议抽象。这是一个刻意的边界选择：gnet 定位是"给你可靠的字节流事件"，不是
"给你一个协议框架"。

### 1.3 goroutine/task 所有权：event-loop 是共享的，阻塞工作显式转交 worker 池

**最关键的设计原则，官方原文直接给出**："你绝不能在 `EventHandler.OnTraffic`
里阻塞 event-loop goroutine"——因为一个 event-loop goroutine 服务多个连接，
阻塞它等于让同一个 reactor 上的所有其它连接一起卡住。

所有权模型：event-loop 数量远小于连接数量（M 个 event loop 服务 N 个连接，
M ≪ N），每个连接在生命周期内被稳定分配给某一个 event loop（"多 reactor"
里的负载均衡三选一：轮询/源地址哈希/最少连接数决定分到哪个 reactor）。真正
可能阻塞的业务逻辑，靠显式调用把工作丢进一个通过 `ants`（第三方 goroutine
池库）实现的 worker 池——**不是每个连接一个 goroutine，是"连接注册在某个
event loop 上，阻塞工作按需借用一个共享池子里的 goroutine"**。

### 1.4 背压与优雅关闭

**没有查到官方文档对这两点的详细说明**（标注不确定，Overview 页面明确未覆盖）。

## 2. cloudwego/netpoll（Go，字节跳动，连接管理 + 零拷贝缓冲）

**定位**：面向 RPC 场景的高性能非阻塞 I/O 网络库，字节跳动出品，是他们
Kitex/Hertz 等 RPC/HTTP 框架的底层网络层。

### 2.1 连接生命周期：三个显式钩子，"连接感知"而非"读到错误才知道"

```
OnPrepare  — 服务端接受新连接时触发，可在此做初始化并返回一个 context 供后续使用
OnRequest  — 触发于读事件，处理输入数据与业务逻辑
CloseCallback — 连接关闭时触发（对端主动断开或本地主动关闭都会触发）
```

一个特别值得注意的设计陈述："net.Conn 没有 API 可以检查连接是否存活，导致
很难为 RPC 框架做出高效的连接池——池子里可能堆积大量已失效的连接。"
netpoll 通过"主动感知连接状态、主动触发回调"解决这个问题，而不是"等下一次
读写失败才知道连接已经死了"——这是它与标准库 `net.Conn` 最核心的差异定位。

**没有查到的信息**：`CloseCallback` 具体在什么条件下判定"对端已断开"（是
读到 EOF 就立刻触发，还是有额外的存活探测机制），guide 文档没有给出细节。

### 2.2 分层模型：四层，缓冲区是独立的一等公民

- **事件层**：`MainReactor`（管理监听器）+ `SubReactor`（监控已分配的连接，
  用 epoll Level Trigger 策略监听 fd 的读/写/关闭事件，回调触发）。
- **缓冲区层**：Nocopy Buffer，"链表数组"结构，支持"读写并行、无锁"。
- **协议层**：连接复用给出的例子是"Thrift Header Protocol"，靠消息头保证
  数据包完整性——即协议解析被明确列为独立的一层，不与事件层混在一起。
- **处理层**：用 goroutine 池（`gopool`）集中处理 I/O 任务，"减少 goroutine
  数量与调度开销"。

**零拷贝缓冲的具体机制**：Nocopy API 直接操作缓冲区的原始地址，通过引用
计数实现资源的自动回收与复用；写缓冲区分两态——`Malloc` 预分配的内存先不
可读，提交（如 `Flush`）后才变成可读数据。这是一个"预分配后再提交"的两阶段
写模型，目的是减少写路径上的内存拷贝次数。

### 2.3 goroutine 所有权：共享 event-loop + 集中式 goroutine 池

与 gnet 同构：不是一个连接一个 goroutine，是 `SubReactor` 共享处理多个连接，
`gopool` 集中处理 I/O 任务以"减少 goroutine 数量和调度开销"。文档提到一个
具体的调度问题："`SubReactor` 本身也是一个 goroutine，会受调度影响，不能
保证立即被执行"——这是共享 event-loop 模型天然要承受的代价（对比
goroutine-per-connection 模型下每个连接的处理时机只取决于自己的 goroutine
何时被调度，不会被同 reactor 上其它连接的处理耗时拖慢）。

### 2.4 背压与优雅关闭

`EventLoop.Shutdown(ctx)`——接受一个带超时的 context 协调关闭前的清理工作，
是明确文档化的 API。**背压机制没有查到具体说明**（标注不确定）。

## 3. Netty（Java，教科书级的 pipeline/ChannelHandler 分层）

**定位**：Java 生态事实标准的异步事件驱动网络框架，Dubbo/gRPC-Java 等大量
上层框架构建在它之上。信息源为官方 API 文档与 DeepWiki 的二手整理（DeepWiki
不是 Netty 官方资料，已标注）。

### 3.1 连接生命周期：四态 + 自动触发的 pipeline 事件

```
Unregistered → Registered → Active → Inactive → (Unregistered)
```

- **Unregistered**：Channel 已创建，尚未关联到任何 EventLoop。
- **Registered**：已关联到一个 EventLoop（但可能还没连接上对端）。
- **Active**：已连接到远端对等体，可以收发数据。
- **Inactive**：与远端对等体的连接已断开。

状态转换**自动触发对应的 pipeline 事件**（不需要手工调用）：注册触发
`fireChannelRegistered()`，变为 active 触发 `fireChannelActive()`，变为
inactive 触发 `fireChannelInactive()`，注销触发 `fireChannelUnregistered()`。
这是四种框架里**唯一一个把"连接生命周期"显式建模为一个有限状态集合、且
状态转换是框架自动完成而非用户手写判断**的设计——gnet/netpoll 都是"回调
触发时刻即状态转换时刻"的隐式模型，Netty 是"先有状态机，状态变化再驱动
事件触发"的显式模型。

### 3.2 分层模型：ChannelPipeline，双向责任链

`ChannelPipeline` 用"拦截过滤器模式"（Intercepting Filter）实现双向链表式
的 handler 链：

- **入站事件**（数据从网络流向应用）：Head → Tail 方向，如
  `channelRead`、`channelActive`。
- **出站事件**（应用向网络写数据/发起连接）：Tail → Head 方向，如
  `write`、`connect`、`bind`。

这个双向结构直接对应"编解码器处理入站分帧、传输 handler 管理连接状态、
业务 handler 操作已解码消息"的分层——**每一层就是链上的一个或几个 handler
节点**，层与层之间的边界不是包/模块边界，是"这个 handler 只关心某一类
消息类型"的约定（如 `LengthFieldBasedFrameDecoder` 只处理"按长度字段分帧"
这一件事，处理完把解码后的对象往下一棒传给下一个 handler）。

**每个 Channel 绑定唯一一个 EventLoop 线程，但多个 Channel 可共享一个
EventLoop**——与 gnet/netpoll 的"共享事件循环"模型是同一个思路，只是 Netty
用"线程"而非"goroutine"，本质上都是"处理单元数 ≪ 连接数"。EventLoop 内部
按优先级处理工作："先处理 selector 上的 I/O 事件，再处理排队的用户任务，
最后执行定时任务"——这是一个明确的、单线程内的任务优先级模型，gnet/netpoll
的对应机制本轮没有查到同等细节。

### 3.3 goroutine（线程）所有权

见 3.2——一个 EventLoop 线程服务多个 Channel，Channel 与线程的绑定在其
生命周期内不变（"exactly one event loop thread"）。

### 3.4 背压与优雅关闭

**本轮检索到的 DeepWiki 页面没有覆盖 Channel 级别的可写性水位线
（high/low watermark）细节**——这是 Netty 实际存在、广为人知的背压机制
（`Channel.isWritable()`、`WriteBufferWaterMark`），但本次检索的具体页面
未涉及，标注为"已知该机制存在但本轮未验证细节来源"，不作为本 RFC 的直接
引用依据。

## 4. Tokio（Rust，异步运行时，BanDB 内核同源思路参照）

**定位**：Rust 生态的异步运行时，不是网络框架本身，但其 task
（轻量级异步执行单元，类似 goroutine）的所有权与生命周期管理模式，是
"每连接一个并发单元"模型下最系统化的官方文档，与 bannet 现有的
goroutine-per-connection 模型范式相同（Tokio task ≈ Go goroutine），
比 gnet/netpoll 的共享事件循环模型更直接可比。

### 4.1 优雅关闭：官方文档给出的三段式模式，有明确命名

Tokio 官方教程把优雅关闭拆成三个显式阶段：

1. **"figuring out when to shut down"**——判断"该关了"这件事本身（如收到
   `ctrl_c()` 信号，或某个 channel 上收到关闭事件）。
2. **"telling things to shut down"**——用 `CancellationToken`（来自
   `tokio-util`）把关闭意图广播给所有已派生的 task："这些 token 允许你
   通知各个 task 应该在收到取消请求时自行终止，从而让优雅关闭的实现变得
   容易。"具体模式：为每个派生的 task 克隆一份 token，task 内部在
   `tokio::select!` 块里监听 `token.cancelled()`；调用一次 `token.cancel()`
   即可同时通知所有持有该 token 的 task。
3. **"waiting for things to finish shutting down"**——用 `TaskTracker`
   确保"真正等到所有工作都完成"："`TaskTracker` 的 `wait` 方法返回一个
   future，只有当它包含的所有 future 都已完成、且 task tracker 本身已被
   关闭时才会 resolve。"

一个容易被忽略但很重要的细节："token 被取消不代表 task 必须立刻终止——
可以先跑一段关闭清理流程再退出"，即 `cancelled()` 是一个"应该开始收尾"的
信号，不是"立刻杀死"的信号。

### 4.2 task 所有权：谁 spawn 谁负责取消

Tokio 的 task 所有权模型很直接："取消一个 future 的方式是 drop 它"，但这
与 `tokio::spawn(future)` 天然冲突——`spawn` 会把 future 的所有权转移进
运行时，调用方手里不再持有它、没法直接 drop。这正是为什么优雅关闭需要
`CancellationToken` 这类显式信号机制：**所有权转移给运行时之后，"谁能让
它停下来"必须靠一个独立于所有权关系的信号通道，而不是靠"持有者去 drop
它"这种默认的 Rust 资源管理方式**。

**运行时关闭时的默认行为**："关闭 Tokio 运行时时（如从 `#[tokio::main]`
返回）会立即取消其上的所有 task"——**阻塞类的同步任务除外**（它们跑在
专门的阻塞线程池上），运行时会无限期等待所有阻塞操作完成，除非显式调用
`shutdown_timeout`。这个"默认立即取消、阻塞任务例外"的设计提示：一个
健壮的关闭模型必须区分"可以被取消信号打断的工作"与"已经在做不可中断的
阻塞 I/O、只能等它自然结束或超时强杀"这两类任务，一刀切的处理方式对
其中一类必然不合适。

### 4.3 已知的实践难点（社区讨论，非官方教程，标注来源层级）

从 GitHub Discussions/Issues（非官方文档，是社区反馈，可信度层级低于
tokio.rs 教程）能看到的共识："这个模式需要不少样板代码——把 token 传给
各个 task、等待它们结束、实现超时机制防止卡死、收集各子系统的返回值"——
即官方推荐的三段式模式解决了"能不能做到优雅关闭"，但没有让它变得低样板，
这是记录在案的已知代价，不是本次调研的推测。

## 6. 对 bannet 重构的启发（不做具体裁决，留给 `docs/rfc/bannet-重构.md`）

- **状态机应该显式化，参照 Netty 的"状态集合 + 自动触发转换"，不是
  gnet/netpoll 的"回调时刻即转换时刻"**——原因是 bannet 目前恰好就是
  "回调时刻即转换时刻"的隐式模型（`StartReader` 里散落的 `return`
  语句各自代表"出错了，该关了"，没有一个统一的状态集合），这正是 RFC
  要解决的问题，Netty 的显式模型是更合适的参照对象，gnet/netpoll 反而是
  "现状问题的另一种呈现方式"，不是解法。
- **并发范式不建议改**：bannet 是 goroutine-per-connection（每连接两个
  goroutine：Reader/Writer），gnet/netpoll 是共享 event-loop——这是两种
  根本不同的范式，径向对比见 RFC 正文的"事件驱动 vs goroutine-per-conn"
  权衡小节，本文档只负责给出两种范式各自的设计事实，不代入 BanDB 的
  具体负载做取舍（那是 RFC 该做的事）。
- **Tokio 的三段式优雅关闭模式（判断→广播→等待）与 bannet 的并发范式同构**
  （都是"每个并发单元独立调度"），比 gnet/netpoll 的"共享循环关闭"更直接
  可参照——`CancellationToken` 对应 Go 的 `context.Context`，`TaskTracker`
  对应某种"等待所有已知 goroutine 退出"的机制（如 `sync.WaitGroup`）。
- **分层边界的落地方式**（拆包 vs Netty 式责任链）不是"抄哪个"的问题，是
  Go 惯用法（包边界 + 接口）与 Java 责任链模式的语言差异——RFC 正文按
  Go 惯用法设计，不生搬 Netty 的 pipeline/handler-context 概念，但会保留
