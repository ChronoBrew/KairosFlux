# dubbo-go Triple 协议调研——给 BANLV v2 的输入

> 调研目的：BANLV v2 RFC（`docs/rfc/BANLV-2.md`）留了几个开放问题（流水线/`corr_id`、
> `flags` 的压缩/流式位、`payload` 的结构化格式）明确写着"等 dubbo-go Triple 协议
> 调研结果作为输入再定"。本文档只做调研，不写代码、不改 RFC 之外的任何东西——
> RFC 的开放问题裁决在 RFC 文档里单独补一节，引用本文档的结论。
>
> 信息源：Apache Dubbo 官方文档（`dubbo.apache.org`）与 dubbogo/triple 的
> GitHub 仓库（均经 WebFetch 检索，日期 2026-08-20）。**没有条件搭建 Triple
> 服务端做实测压测**，性能相关结论全部来自文档自述，已在对应小节标注"未经
> 独立验证"。

## 1. Triple 是什么，为什么被设计出来

Triple 是 Dubbo3 生态的默认协议：一个基于 HTTP 的 RPC 协议，设计上参考了
gRPC、gRPC-Web、通用 HTTP 等多种协议模式，目标是"浏览器可直接访问、与 gRPC
完全兼容、支持流式通信"三者兼得。

官方文档给出的动机是 gRPC 的几条具体短板，不是泛泛的"想做个新协议"：

- **gRPC 被 HTTP/2 交互标准限制**，无法直接给浏览器/HTTP API 用，必须额外接
  grpc-web 之类的代理组件。
- **gRPC 官方库强绑定 Protocol Buffers**，对多语言需求有限的用户是不必要的
  负担（必须学 IDL、走 protoc 工具链）。
- **gRPC 服务调试困难**，需要专门工具，且这些工具往往不成熟。
- **gRPC 协议库代码量巨大**：官方文档给出的具体数字是 gRPC 库"超过 10 万行
  代码"，对比 Dubbo 协议实现"只有几千行"。

这几条动机与 BanDB 选择自研 BANLV 而非直接上 gRPC 的理由（`internal/kvgrpc`
包注释：gRPC 需要 protoc 工具链、把内部传输实现当公开 API 会给使用方增加负担）
在方向上是同构的——都是"不想为了拿到 RPC 能力，被迫接受一整套重量级生态"。
这一点增加了"Triple 的设计取舍值得参考"的可信度，而不只是因为它是同一个
作者群体（dubbo-go）做的。

## 2. 帧模型与 HTTP/2 的关系

Triple 不是单一协议，是**两个子协议叠在一起**，按传输能力自动选择：

- **HTTP/1 子协议**（轻量、仅 Unary）：请求体是裸的 JSON 或 Protobuf 负载，
  **不做长度前缀**，直接放进 HTTP body——这是为了浏览器/`curl` 能直接访问、
  不需要理解 gRPC 的分帧规则。代价：只支持一问一答（Unary），不支持任何流式。
- **HTTP/2 子协议**（与 gRPC 100% 兼容）：复用 gRPC 的 HTTP/2 帧模型——
  请求头通过 `HEADERS + CONTINUATION frames` 传输，`:path` 编码为
  `"/" Service-Name "/" method-name`；负载走 `DATA frames`，消息格式是
  `[Length(4 字节)][Protobuf 消息字节]` 的长度前缀格式。Unary 与四种流式
  （见第 3 节）都走这条子协议。

也就是说，Triple 的"帧模型"本身没有发明新东西——HTTP/2 分支就是原样照抄
gRPC 的分帧规则，只在 HTTP/2 头部里附加了 Dubbo 特有的治理元数据（见第 4 节）。
这是"帧模型与 HTTP/2 关系"这个问题最直接的答案：**关系是"直接复用"，不是
"参考后重新设计"**。

## 3. 流式语义

四种模式：Unary、client-streaming、server-streaming、bi-streaming，全部
建立在 HTTP/2 子协议之上（HTTP/1 子协议只支持 Unary）。协议文本给出的形式化
描述：

```
Request  → Request-Headers *Length-Prefixed-Message EOS
Response → (Response-Headers *Length-Prefixed-Message Trailers) / Trailers-Only
```

- 每条消息前缀 4 字节长度（不区分是 Unary 的唯一一条消息还是流式的第 N 条）。
- `EOS`（End of Stream）标记请求方结束发送——对应 HTTP/2 的 `END_STREAM` 标志。
- 响应要么是"头部 + N 条消息 + Trailers"，要么直接是"Trailers-Only"（如
  请求一开始就被拒绝，不产生任何正文消息）。

**与 BANLV 的对照**：BANLV v1/v2 目前都是"一条连接一次只有一个在途请求"的
严格请求-响应模型（v2 RFC 里 `corr_id` 是为了解锁流水线而预留的字段，但流水线
本身怎么做还没设计）。Triple 的流式模型说明：一旦要支持"服务端持续推多条消息"
这种语义，长度前缀的消息帧 + 一个"流结束"标志是必需的最小结构，不是可有可无
的装饰。

## 4. status/metadata 结构

两条子协议的错误模型完全不同，这是一个容易被忽略但很重要的设计事实：

- **HTTP/1 子协议**：把 Dubbo 内部错误码映射成 HTTP 状态码（文档给出的具体
  映射例子：错误码 30/31 → HTTP 408 超时，错误码 60 → HTTP 404 未找到），
  错误响应体是 `{"status": <code>, "message": "<text>"}` 的 JSON。
- **HTTP/2 子协议**：严格遵循 gRPC 的 trailer 模型——`grpc-status` 与
  `grpc-message` 出现在带 `END_STREAM` 标志的最后一个 `HEADERS frame`（也就是
  gRPC 的"trailers"），不是普通的响应头，也不是响应体里的字段。

除了错误状态，Triple 在 HTTP/2 头部里还夹带 Dubbo 治理专用的元数据，
不属于 gRPC 标准但与 gRPC 头部共存（gRPC 对不认识的头部按规范应忽略，
不会因为多了几个头就拒绝）：`tri-service-version`、`tri-service-group`
（服务版本/分组隔离，Dubbo 的多版本路由靠它）、`tri-req-id`、
`tri-trace-traceid`、`tri-trace-rpcid`（链路追踪）、`tri-unit-info`。

**与 BANLV 的对照**：BANLV v1.1 刚给 `dropped` 响应加的
`[reasonLen u16][reason]` 扩展字段，本质上做的是同一件事——在"成功/失败"
这个二元状态之外，用一个独立的、老客户端会忽略的追加字段承载更丰富的错误
上下文。Triple 用两套完全不同的错误模型（HTTP 状态码 vs gRPC trailer）服务
两条子协议，而不是勉强用一套模型兼容两边——这提示 BANLV v2 与 RFC C 段要设计
的"机读错误码分类学"也不必强求单一表示，可以按传输场景分层设计（见 RFC 补篇）。

## 5. 协商与版本演进

**没有找到"显式版本协商握手"的证据**——这不是遗漏，是这个协议确实没有设计
这样一个步骤。Triple 用两种机制处理"这是不是 Triple 请求"的问题，都属于
"检测/拒绝"而非"协商"：

- **`TRI-Protocol-Version` 头部强制**：官方规范要求所有 Dubbo 客户端实现在
  请求里带上 `TRI-Protocol-Version`；服务端可以拒绝不带这个头的请求，返回
  HTTP 400。这解决的问题很具体：区分"这是 Triple 请求"还是"这只是一个凑巧
  格式相似的 application/json 请求"，不是"协商双方都支持的协议版本、选一个
  兼容版本使用"。
- **端口复用的协议探测（ProtocolDetector）**：Dubbo 支持一个端口同时服务
  HTTP/1、HTTP/2、gRPC、Triple、甚至老的 Dubbo2 二进制协议，靠一个
  `ProtocolDetector` 组件在连接建立后、读到客户端第一个消息时识别协议类型，
  再把连接绑定到对应的处理逻辑（`WireProtocol`）。**这里有一个明确的调研
  局限**：检索到的资料只描述了"读第一条消息去识别"这个流程，没有给出具体
  检测的字节序列/魔数细节，也没有确认这是否需要缓冲/回放已读字节（用于把
  已消费的探测字节"还给"后续的协议解析器）——这是我没能验证到的实现细节，
  标注为不确定，不代入 RFC 的裁决依据。

**与 BANLV 的对照**：BANLV v2 RFC 设计的协商方案（v2 客户端先发 v1 格式的
HELLO 帧，靠"有没有收到响应"的超时来判断对端是 v1 还是 v2）与 Triple 的做法
本质上更接近——**都是"先试探、按结果推断"，不是"先握手、协商出共同支持的
版本"**。Triple 的"强制头部+拒绝"模式（多用于区分协议家族，如 Triple vs
纯 JSON）比 BANLV v2 要解决的问题（同一个协议的 v1 vs v2）更粗粒度，直接照抄
不合适；但"端口复用探测"这条思路提示 BANLV 未来如果要在同一个端口上支持
BANLV v1、BANLV v2、甚至 gRPC，可以参考"连接建立后读首个消息再决定处理器"
这个骨架，而不是像现在的 RFC 草案那样让协商发生在"应用层再发一个专门的
HELLO 请求"——但这个方向本轮不展开，留给 RFC 需要真正扩到多协议共存时再评估。

## 6. 与 gRPC 兼容层怎么做的

答案出乎意料地简单：**Triple 的 HTTP/2 子协议本身就是 gRPC 的线格式**，
不是"翻译层"或"适配层"。同样的 `HEADERS`/`DATA` 帧结构、同样的长度前缀消息
格式、同样的 `grpc-status`/`grpc-message` trailer——一个标准 gRPC 客户端能
直接和 Triple 服务端通信，反过来也一样，文档原话是"100% compatible with
gRPC protocol"。

"兼容层"实际做的事情只有一件：**在 gRPC 标准头部之外附加 Dubbo 专有的
`tri-*` 头部**。因为 HTTP/2（以及 gRPC 建立在其上的头部模型）对不认识的头部
按规范应该忽略而非拒绝，这些额外头部对标准 gRPC 客户端是透明的——Dubbo 生态
内的客户端认得它们、用来做服务治理，生态外的 gRPC 客户端就当没看见。

**这是一个对 BANLV 有直接借鉴价值的模式**：不需要为兼容性设计一个独立的
转换/适配层，只要新协议是旧协议的**超集**（多加字段，不改变、不复用已有
字段的语义），旧实现就能在"不认识新字段就忽略"的前提下继续工作。BANLV v1.1
的 dropped-reason 扩展已经是这个模式的一个小规模实践（见第 4 节）；v2 RFC
如果要谈"v2 服务端要不要理解 v1 帧"，这个"超集不动旧字段"的原则同样适用，
比"检测版本后分叉出两套完全独立的解析逻辑"更省心，虽然 v2 目前头部结构与 v1
差异较大（定长 vs 变长 msgID），做不到严格意义上的"字段超集"，只能退而求其次
用第 5 节的探测机制。

## 7. 为兼容性付出的性能代价（证据薄弱，标注不确定）

**没有找到令人信服的头对头性能数据**。官方文档的原话是 Java 实现"性能与
grpc-java 持平，有时更好，尽管复杂度更低"——这是一句自述，不是可复现的压测
报告，也没有给出具体数字、测试方法、硬件环境。**不采信这句话作为"Triple
没有兼容性代价"的证据**，只记录官方是这么宣称的。

真正找得到、可以确认的代价点只有两个，都不是"HTTP/2 层"的代价，而是设计
取舍本身带来的：

1. **HTTP/1 子协议放弃了流式能力**，换取浏览器/curl 直接可用——这是文档
   明确承认的权衡，不是隐藏代价。
2. **端口复用的协议探测**（第 5 节）在连接建立时多一次"读第一条消息再决定
   处理器"的判断开销——量级未知（调研没有找到具体数字），但架构上这确实是
   每连接一次性的额外成本，不是零成本。

**BANLV 的参考意义**：与其说"Triple 证明了兼容性可以零代价"，不如说"Triple
把代价都花在了协议设计的取舍点上（HTTP/1 放弃流式），而不是运行时的动态
转换开销上"——这与 BANLV v1 一直以来"零依赖、不做运行时反射/动态分发"的
工程取向是一致的，是本轮调研里最值得 BANLV v2 直接借鉴的一条原则性结论，
即便它不是一条具体的协议字段设计。

## 8. 逐机制裁决表：BANLV v2 该不该借鉴

| Triple 机制 | 是什么 | 为什么这么设计 | BANLV v2 该不该借鉴 |
|---|---|---|---|
| HTTP/2 帧模型直接照抄 gRPC | 不发明新分帧规则，长度前缀消息 + HEADERS/DATA/Trailers | 换取与整个 gRPC 生态零成本互通 | **不适用**：BANLV 不建在 HTTP/2 之上，没有"要不要抄 gRPC 分帧"这个选项；但"消息长度前缀"本身（BANLV v1/v2 都有）是同一个基本思路的独立发明，无需改动。 |
| 流式消息用 4 字节长度前缀 + EOS 标志 | 流式场景下每条消息定长前缀，一个显式的"流结束"信号 | 多条消息共享一条连接时的最小分隔结构 | **v2 若真做流水线/流式，值得借鉴**：RFC 的 `corr_id` 解决"响应对应哪个请求"，但没有解决"一个请求对应多条响应"——如果 v2 未来要支持服务端流式推送，需要一个类似 EOS 的显式流结束标志，现有 `flags` 字段可以留一位给它（RFC 已列为开放问题，本次调研确认这是必须的最小结构，不是可选装饰）。 |
| 两套独立的错误模型服务两条子协议 | HTTP 状态码 vs gRPC trailer，不强求统一 | 承认不同传输层的错误期望不同，不为了"一致性"牺牲各自的自然表达方式 | **部分借鉴**：RFC C 段设计的"机读错误码分类学"不必追求让同一套码同时优雅服务所有场景，允许按场景（如 BANLV 原生 vs 未来可能的 HTTP 网关）分层，但底层错误"事实"（如 ErrDropped 的具体 reason）应该是同一个来源，只是表现形式可以不同——对应 RFC 补篇的 Schema Descriptor 里 `ErrorCodes` 作为单一声明来源的设计。 |
| 版本区分靠强制头部 + 拒绝，不是握手协商 | `TRI-Protocol-Version` 缺失即拒绝（400） | 区分的是"协议家族"（Triple vs 普通 JSON），粒度粗，不需要复杂协商 | **不直接适用**：BANLV v2 要区分的是同一协议的两个版本（v1/v2），粒度更细，RFC 已经选了更合适的"发 HELLO、按超时推断"方案，不需要改。 |
| 端口复用协议探测（读首个消息再分发） | 一个端口同时服务多种协议，运行时识别 | 部署简化：不用为每种协议开独立端口 | **本轮不借鉴，记为未来方向**：BANLV 当前没有"一个端口服务多协议"的需求（gRPC 走独立端口，`cmd/ban-grpc-server` 明确是基准对照用的独立服务）。如果未来真的要在同一端口上同时服务 BANLV v1/v2，这个"连接建立后读首条消息再决定处理器"的骨架值得回来参考，但探测的具体实现细节本轮调研没有查全（见第 5 节的不确定标注），届时需要补做实现层面的调研。 |
| 新协议是旧协议的"字段超集"而非平行分叉 | gRPC 标准头部之外加 Dubbo 专有头部，旧客户端忽略新字段 | 兼容性靠"新字段可被安全忽略"，不靠运行时转换 | **已经在用，继续坚持**：BANLV v1.1 的 dropped-reason 扩展就是这个模式；v2 头部结构变动较大（定长头部 vs v1 变长 msgID），做不到严格字段超集，只能退回协议探测/协商，但**v2 内部的后续演进**（如 §7 提到的 `type` 号治理、`flags` 位含义扩展）应该继续遵循这条原则，优先加字段而非改变已有字段语义。 |
| "兼容性代价花在设计取舍点，不花在运行时转换" | HTTP/1 放弃流式换简单性，而非运行时协议翻译 | 保持 gRPC 兼容不通过写一层转换代码，而是让 HTTP/2 层直接复用 gRPC 格式 | **原则性借鉴，非具体字段**：BANLV v2 若要在 v1/v2 之间提供某种互操作，应优先考虑"降级到对方能懂的格式"（RFC 现有方案就是这样：v2 探测到对端是 v1 就整体切换到 v1 帧格式），而不是引入一个双向转换层——这与 Triple 的取向一致，是本轮调研对 RFC 现有设计的一次确认而非新增。 |

## 9. 不确定处汇总

- 端口复用协议探测（ProtocolDetector）的具体字节级识别逻辑：**未查到**，
  官方文章明确表示细节在示例代码仓库（`dubbo-samples-port-unification`），
  本轮未去看该仓库源码。
- "Triple 性能与 grpc-java 持平甚至更好"：**官方自述，非独立压测数据**，
  不采信为设计依据。
- dubbo-go（Go 实现）与 Java 版 Triple 在协议细节上是否完全一致：本轮主要
  查的是协议规范文档与 `dubbogo/triple` 仓库的 README，**没有去读 Go 实现
  源码逐行核对**，规范层面的结论视为对 Go 实现同样成立（规范文档明确是
  跨语言的协议规范，不是 Java 专属），但如果后续要精确抄某个字段的字节
  布局，仍需去读 Go 源码确认，不能只信规范文字描述。
- Dubbo2 与 Dubbo3/Triple 之间的兼容性细节（如老 Dubbo2 二进制协议的客户端
  如何与 Triple 服务端互通）：本轮未深入调研，与 BANLV v2 的相关性也较低
  （BANLV 没有"v0"协议要兼容），故未展开。
