# 迭代复盘：读路径的 syscall 与分配——点查从 12.6k 到 18.7 万 QPS

日期：2026-08-13　范围：`storage`（透传到 `service` 读路径）

## 背景

压测口径此前用 `-n 10000` 个 key，恰好等于 `MaxMemTableSize`，于是 GET 几乎全部命中内存表——**磁盘读路径从未被测到**。把工作集提到 20 万 key（远超单张内存表）后，差距立刻显形：

| 场景（50 并发 GET） | QPS | P50 |
| --- | --- | --- |
| 工作集常驻内存表 | 116,513 | 248µs |
| 工作集 20 万 key（下穿 SSTable） | **12,586** | 2.85ms |

同机同并发差 9.3×，headroom 全在磁盘读路径。

## 量化：一次点查花在哪

读一个 key 的代价被三处放大：

1. `searchBlock` **每次点查都 `os.Open`/`Close` 一次文件**，随后用 `binary.Read` 逐字段读块内条目——单个 64 条目的块约 **250 次 read syscall**。
2. `GetAllMata()` 每次调用加读锁并**复制整个元数据切片**，而点查每次都要调它逆序遍历判 newest-wins。
3. 命中块后每次为整块（约 18KB）**新分配一次缓冲**；4 万 QPS 下即数百 MB/s 的分配 churn。

## 优化

**常驻句柄 + 单次整块读取**。块长度可由块索引推出（`下一块起始 − 本块起始`，末块用 footer 里的 `indexOffset`，一并缓存为 `blockIndex.dataEnd`），故**无需变更磁盘格式**即可按精确长度一次 `ReadAt` 读走整块、在内存中扫描。读路径统一用 `ReadAt`——它不依赖文件内偏移，故共享句柄可被并发读者安全复用；句柄在 `DeleteSSTable` 中随索引/布隆缓存一并剔除，否则每轮 compaction 泄漏一个 fd。

**元数据改 copy-on-write 原子快照**。`metas` 仍是持锁修改的主副本，每次变更后发布一份不可变快照，读侧经 `atomic.Pointer` 无锁零拷贝获取。变更频率是刷盘/合并级，远低于读。

**分片 LRU 块缓存**（默认 64MiB，`BlockCacheBytes` 可调）。SSTable 一经写入即只读，块内容不可变，故缓存条目可被并发读者共享而无需拷贝；命中路径既无磁盘访问也无整块分配。分 16 片降低锁竞争；单块超过分片预算时不入缓存，避免其反复挤空该分片。

**消除每请求分配**：`hash/fnv` 的 `New64a()` 返回接口、构造即逃逸到堆，`Write` 还需 `[]byte(path)` 再分配一次——就地展开 FNV-1a 并按字节遍历字符串，零分配；帧编解码由 `bytes.Buffer` + 反射式 `binary.Write` 改为按最终长度一次分配并直写。

## 验证

| 阶段 | QPS | P50 | P99 |
| --- | --- | --- | --- |
| 基线 | 12,586 | 2.85ms | 24.83ms |
| + 单次整块读取 | 41,053 | 473µs | 12.43ms |
| + 块缓存 | 167,814 | 195µs | 1.92ms |

**累计 13.3×，P50 降低 14.6×。** 去分配一项单独用交替 A/B 测得 **+6.1%**（175,991 → 186,783）。

一处回归修复：整块解析中 `append([]byte(nil), v...)` 在空 value 时返回 nil，会把「空 value」误判为「墓碑」，由既有用例 `TestMemTableEmptyValueNotTombstone` 拦下。

## 后续

- 块内改二分（restart points）需变更磁盘格式，而块内扫描已在内存中且 ≤64 条目，预期收益低。
- 本机压测客户端与服务端共享 8 核，故该数字含客户端开销，是「同机端到端」口径。

## 方法学教训

本机顺序测 before/after **不可靠**：同一份二进制可从 187k 漂到 130k（热节流），曾据此误判为性能回归。小幅改动一律用**交替 A/B** 抵消漂移。
