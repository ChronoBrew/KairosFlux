# 迭代复盘：扫描覆盖 SSTable——下游投递曾静默漏投所有已落盘记录

日期：2026-08-13　范围：`storage`（`ScanRange`）、`service/delivery`

## 背景

问「功能还能优化什么」，第一件查出来的不是缺功能，是**核心功能在静默丢数据**。

```
写入 200 条，等 flush 落定：
  逐个 Get  → 命中 200 条
  ScanRange → 看到   0 条
```

`ScanRange` 只遍历 `active` 与 `dirty` 两张内存表，**已 flush 的数据对扫描完全不可见**。两条读路径的可见范围不一致，所以极难察觉。

## 后果不止 SCAN 少返回结果

下游投递正是按游标反复调用 `Scan` 取数：

```
delivery.KVSource.Fetch(cursor) → kv.Scan(cursor, end) → Engine.ScanRange   ← 只看内存表
```

flush 阈值上万条、投递每秒百条——**flush 必然快于投递**，落盘的记录于是再也不会被投递。「摄入缓冲 + 可靠投递」是本项目的头号能力，这里却在漏投。

## 优化：多路归并

复用 compaction 已有的归并迭代器：抽出 `entryIterator` 接口，让内存表快照与 SSTable 文件迭代器混合参与。源序按新旧排列（SSTable 由旧到新 → `dirty` → `active`），故同 key 只保留最新版本；最新版本是墓碑时整条跳过。

**锁的处理**：内存表在锁内按范围拷出快照，锁外做归并。归并要读磁盘——全程持锁会让写入停等 I/O，而无锁遍历跳表又会与并发写相争（`Get` 曾因此出错）。拷贝量由内存表大小天然有界。

## 一个必须一起解决的复杂度问题

按游标扫描必须能**跳过前缀**，否则投递总代价随数据量平方增长。首版顺序跳过小于 `start` 的条目，端到端实测 2000 条投递 6 秒只完成 810 条。

两处修正：
1. 借**块索引二分**定位到目标块起点（该索引点查早已在用）；无块索引时退回从头读，正确性由范围裁剪保证。
2. 先按文件的 `[MinKey,MaxKey]` **排除与区间无交集的文件**，避免为它白开一个迭代器。
3. `limit` 一路传到扫描里：`KVServer.Scan` 此前总把从游标到键空间末尾的条目（上限 1 万）全部物化，而调用方只取前几百条。

Fetch 取 201 条的耗时随游标推进：**13ms → 3.5ms → 0.9ms**（后续迭代器改缓冲读后进一步降到 13ms → 1.57ms → 0.12ms）。

## 验证

- 存储层与 service 层各加回归用例，含**覆盖写与墓碑跨 SSTable 的新旧判定**。
- **变异验证**：退回只扫内存表后用例立即失败。
- 端到端：`MaxMemTableSize=50` 写入 2000 条产生 **56 个 SSTable**，投递收敛到 **2000/2000**、零错误。
- 读吞吐用交替 A/B 核对无回归（180,556 vs 171,419；166,164 vs 158,165，分支两次均略快）。

## 语义边界（已写入 `source.go` 注释）

`KVSource` 按 **key 升序**推进游标，`IdempotentFileSink` 按「已投递的最大 key」过滤——两者都假设投递顺序与 key 顺序一致。若写入乱序（多个 writer 并发写分散在整个键空间的 key），投递游标可能已越过某位置，而更小的 key 此后才落地：**那些记录永远排在游标之前，不会再被投递**。

对照实测：2000 条若在投递启动前写完，10 轮取满 **2000/2000**；与 20 个并发 writer 同时进行则只投出约 **310** 条。

要覆盖乱序到达，游标需改为按「写入序」而非「key 序」推进（为每条写入分配单调序号并按其建索引），属独立设计。当前实现适用于时间序 key（如 `imu:dev0:<ts>`）这类天然单调的摄入场景。

## 后续

投递游标改按写入序是本项目距离「可靠投递」最实质的一步——它同时解决漏投与「回收误删未投数据」两件事。
