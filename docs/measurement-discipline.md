# 测量纪律：本轮优化里踩过的坑与固化下来的规矩

日期：2026-08-13　范围：方法学（适用于本仓全部优化与测试）

本轮优化的收益大部分不来自「想到了聪明办法」，而来自**把测量做对**。以下每条都是被真实误判换来的。

## 1. 顺序测 before/after 不可靠——用交替 A/B

同一份未改动的二进制，本机可从 **187k QPS 漂到 130k**（热节流），漂幅约 ±16%。据顺序测量我曾误判某次改动为「性能回归」。

**规矩**：改动幅度小于 30% 时，一律交替运行 A、B、A、B… 取同轮对比，让漂移落在两侧而非只落在后测的一侧。

## 2. 压测口径要先确认它压到了目标路径

首轮读压测用 `-n 10000`，恰好等于 `MaxMemTableSize`，于是 GET **几乎全部命中内存表，磁盘读路径从未被测到**。把工作集提到 20 万后，QPS 从 116k 掉到 12.5k——真实瓶颈才显形。

**规矩**：报吞吐数字前，先说明它走的是哪条路径，并用一个反向口径（更大/更小工作集）确认。

## 3. 优化前先量「瓶颈是否真的在那里」

分片 WAL 看起来必然有效。先测两件事把它否决了：设备并发 fsync 只给 2.4×（16 分片），而 WAL 自身在 50 并发下已能跑 5,581/s、整条 PUT 路径却只有 1,327 QPS——**4.2× 的成本在 WAL 之上**。真根因是一个拼错的配置键。事后反向实测：分片让写**慢 4.4 倍**。

**规矩**：先归因，再优化。归因手段优先用「隔离基准 + goroutine 采样」，而不是直觉。

## 4. 「优化无效」和「优化没生效」在数字上一模一样

迭代器改缓冲读后基准显示 261ms → 270ms。诱人的结论是「syscall 不是瓶颈，页缓存已经吃掉了」。去核对代码才发现替换串写错（找 `it.r`，原文是 `it.f`），**`Next()` 根本没被改到**。修正后 24×。

**规矩**：看到「没有改善」，先确认改动真的进入了热路径，再解释为什么没有改善。

## 5. 变异测试：证明测试真的在守护不变量

一个从未失败过的测试可能什么都没测。本轮对每个关键守卫都做了反向注入：

| 注入的错误 | 期望 |
| --- | --- |
| 合并失败仍删源文件 | compaction 故障用例失败 |
| 元信息加载退回 `go`（异步） | 启动契约用例失败 |
| 扫描退回只看内存表 | 扫描覆盖用例失败 |
| `config.json` 加一个拼错的键 | 严格解码用例失败 |

## 6. 错误路径要靠故障注入，不靠 review

四处静默丢数据全部出自「正常路径全绿、错误路径无人测」。可移植的注入手法比精巧的手法更有价值：

- 自定义 `io.Writer` 在第 N 字节后报错，**遍历尾部每一个字节位置**（纯内存，无需磁盘条件）。
- 在 `.tmp` 路径上放一个**目录**，使 `OpenFile` 必然失败（不依赖磁盘写满或权限）。
- 依赖权限的注入（只读目录）必须**先探测是否真的生效**，root 下 `t.Skip` 而非给出假绿。

## 7. 并发缺陷要在 `-race` 下压，不是压得更久

两处数据竞争（`Engine.Get` 无锁遍历跳表、`ConnManager.Len` 无锁读 map）都在最热路径上，却长期未被发现——压测走编译好的二进制、不开 race 检测，负载再大也只是把竞争窗口踩得更频繁而不报错。

**规矩**：`go test -race ./...` 是合并前门槛；新增并发能力时同时新增「并发压同一实例」的用例。

## 8. 端到端脚本先怀疑自己

本轮 E2E 测量被三个自伤问题污染过：上一轮 `kairosflux-server` 未退出（新进程 `writes=0` 却在回收——负载打到了旧进程）、数据目录相对路径解析到仓库之外、写入阶段与观测窗口重叠。

**规矩**：吞吐先在**单元层**量（隔离基准），E2E 只用于最终确认；E2E 脚本必须自证「端口归本进程」「目录正确」「阶段不重叠」。

## 9. 用 grep 计数得到的「事实」要复核

我曾用 `grep -i` 统计术语混用，把**标识符引用**当成散文计数，据此宣称「术语五五混用、某词 32 次」，实际散文里只有 2 次。

**规矩**：任何用于支撑结论的计数，都要抽样核对它数到的是不是你想数的东西。
