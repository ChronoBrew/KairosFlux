# 迭代复盘：写路径归因——一个配置键拼错吃掉 4.83× 吞吐，并证伪分片 WAL

日期：2026-08-13　范围：`config`、`storage`（WAL）、`bannet`

## 背景

写路径基线：50 并发 PUT 仅 **1,327 QPS、P50 37.85ms**。直觉方案是分片 WAL（多文件并发 fsync）。按本仓「测量优先」纪律，动手前先量两件事。

## 量化一：设备的 fsync 可扩展性

N 个文件各自独占一个 goroutine 反复 append + `Sync`，聚合吞吐：

| 分片数 | 聚合 fsync/s | 单次延迟 |
| --- | --- | --- |
| 1 | 254 | 3.94ms |
| 2 | 254 | 7.89ms |
| 4 | 348 | 11.49ms |
| 8 | 563 | 14.23ms |
| 16 | 613 | 26.31ms |

**16 个文件只换来 2.4×，且单次延迟恶化 6.7 倍**——macOS 的 `F_FULLFSYNC` 是全设备缓存刷新，并发 fsync 在设备层大幅串行化。分片 WAL 是弱杠杆。

## 量化二：瓶颈到底在 WAL 之内还是之上

`BenchmarkWALAppendConcurrent`（仅驱动 WAL，不经网络与内存表）：

| 并发 | append/s |
| --- | --- |
| 1 | 249 |
| 8 | 924 |
| 50 | **5,581** |
| 200 | 23,787 |

WAL 自身在 50 并发下能跑 5,581/s，而整条 PUT 路径只有 1,327 QPS——**4.2× 的成本在 WAL 之上，不在 fsync**。分片 WAL 被否决。

## 根因：worker 池配置键静默失效

goroutine 采样显示：负载中**恒定只有 10 个 goroutine 位于 `WAL.Append`**，而客户端有 50 并发在途。

`config.json` 写的是 `WorkPoolSize` / `MaxWorkPoolTaskLen`，结构体字段却是 `WorkerPoolSize` / `MaxWorkerTaskLen`。`json.Unmarshal` 匹配不上即**静默忽略**，worker 池取默认值 10 而非配置意图的 100。每个 worker 串行处理其队列，故在途请求被硬性封顶为 10 → group commit 每批只能攒约 10 条而非 50 条 → 一次 fsync 的摊薄倍数下降 5 倍。

## 优化与验证

修正键名后：

| | 改前 | 改后 | 倍数 |
| --- | --- | --- | --- |
| PUT QPS（50 并发） | 1,327 | **6,415** | 4.83× |
| PUT P50 | 37.85ms | **7.66ms** | 4.9× |

修复后整条路径（6,415）已略高于 WAL 独立基准（5,581），即**写路径抵达 fsync 物理上界**，其上无剩余 headroom。

## 反向验证：分片 WAL 会让写变慢

固定 50 总并发，单 WAL vs N 个各自 group commit 的 WAL（按 key 散列路由）：

| 分片数 | append/s | 相对 |
| --- | --- | --- |
| 1 | 5,996 | 1.00× |
| 2 | 3,856 | 0.64× |
| 4 | 2,109 | 0.35× |
| 8 | 1,374 | **0.23×** |

**分片使写慢 4.4 倍**：group commit 已把 50 个并发写摊销为一次 fsync，分片把批次缩小 N 倍去换并发 fsync，而设备只给 2.4×，方向相反。结论固化为基准用例保留，避免后续重复投入。

## 防回归

新增 `config` 严格解码测试：以 `DisallowUnknownFields` 解码随仓库发布的 `config.json`，任何拼错/已重命名的键立即失败；并以一个拼错的键证明该守卫确有效力。「配置键静默失效」这一缺陷类不再可能无声复现。

## 后续

- 单设备下「单 WAL + group commit + 充分在途并发」已是最优形态，写延迟下界即 `F_FULLFSYNC`（本机 3.94ms）。
- 再提升需放松持久性契约（`Append` 返回即 fsync），属产品决策；分布式系统里安全放松本地 fsync 的标准答案是**复制**而非客户端重传。
