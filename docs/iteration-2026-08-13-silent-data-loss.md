# 迭代复盘：故障注入测出四处静默丢数据——正常路径全绿，错误路径无人测

日期：2026-08-13　范围：`storage`（SSTable 写尾、全量读、元信息加载）

## 背景

巡检 SSTable 写路径时发现块索引与 Footer 的写入**丢弃了全部返回值**（`binary.Write` / `file.Write` 共 8 处），定位偏移的 `file.Seek` 也用 `_` 忽略错误。由此展开一轮故障注入，又连带测出三处缺陷。四处的共同特征：**正常路径全绿，错误路径从未被测**。

## 缺陷一：写尾吞掉 I/O 错误

后果不是「少写几个字节」，而是两侧夹击的静默丢数据：

- **读侧**：尾部残缺 → footer magic 校验失败 → 重启时 `MaxKey` 无从得知，若据推导值过滤，`[MinKey,MaxKey]` 会把命中 key 整段跳过。
- **写侧**：调用方以为落盘成功，于是**销毁另一份副本**——`Flush` 把 `dirty` 置 nil 丢弃内存中唯一副本；`CompactSSTable` 删除全部源文件。

`Seek` 失败时 `indexStart` 为 0，Footer 会声称块索引位于数据区起点。

**修法**：`WriteToSSTable` 与 `MergeSSTable` 的写尾逻辑本就完全相同（原注释即写明），合并为单一 `writeTail`，逐段检查并包裹出失败段落。读路径只有一份解析实现，写路径也只留一份。

另两类未检查的写经核对是**安全的**，补注释固定不变量而非加噪声：数据段先写 `bytes.Buffer`（其 `Write` 按文档永不返回错误）；`MergeSSTable` 的数据循环写 `bufio.Writer`（错误具粘性，首个错误会在已被检查的 `Flush()` 处浮现）。

## 缺陷二 / 三：尾部残缺的文件，整份数据都读不到

写了「截掉尾部后数据段仍应可读」的用例，**测试立刻失败——连第一个 key 都读不到**：

```
写入 200 条，等 flush 落定：
  逐个 Get  → 命中 200 条
  ScanRange → 看到   0 条
```

追下去是两处叠加：

1. `ReadAllFromSSTable` **从错误的偏移开始解析**。`readDataEndOffset` 为读 footer 已把偏移 seek 到文件末尾附近，而「移回开头」写在 `if dataEnd > 0` 的条件里——没有 footer 的文件因此从末尾开始解析，恒返回 0 条。**老格式的全量读回退路径实际从未生效。**
2. **解析失败即让整次读取失败**：任一记录解不出时 `return nil, err`，而唯一调用方 `readFromSSTableFull` 丢弃该错误后遍历 nil 切片。改为就地停止、返回已解出的条目——与 `WAL.Replay` 对撕裂尾写的处理一致，理由也相同：数据区总是先于尾部写出，无法解析的字节只可能出现在有效数据之后。

连带去掉 `MaxKey` 的不安全推导（`EnsureMeta` 顺序扫描会把索引/布隆/footer 当记录读出）。改为 `MaxKeyKnown` 语义：仅当 MaxKey 取自块索引或写入时填入才可信，不可信则**不施加上界**。多扫一个文件是可接受的代价，漏读不是。

## 缺陷四：启动期 flush 的元信息被异步扫描抹掉

写 compaction 故障注入时，一个断言「失败后 L0 仍有 3 个文件」的用例报告了 **4 个**——同一路径在 `metas` 里出现两次，磁盘上只有一份。

`LoadSSTableMetaList` **整体替换** `metas`，而 `NewEngine` 以 goroutine 启动它，于是与并发的 `AddMeta` 相争。生产路径可达：

```
NewKVServer → NewEngine()（扫描在后台开始）
            → replayWAL()（重放触发 flush → AddMeta 登记新 SSTable）
            → 扫描完成，metas 被整体覆盖 → 刚登记的那条没了
```

该 SSTable 的数据直到下次重启前都读不到，而**出问题的位置恰好是崩溃恢复路径**。改为同步加载：引擎在知道磁盘上有哪些 SSTable 之前不应对外服务。

## 故障注入手法

| 目标 | 注入方式 | 可移植性 |
| --- | --- | --- |
| 写尾失败 | 自定义 `io.Writer` 在第 N 字节后报错，遍历**尾部每一个字节位置** | 纯内存 |
| WAL 重写失败 | 在 `.tmp` 路径上放一个**目录**，使 `OpenFile` 必然失败 | 不依赖磁盘写满或权限 |
| compaction 失败 | 把 SSTable 目录改为只读 | 依赖权限，故先探测能否创建文件，root 下 `t.Skip` 而非假绿 |
| 尾部残缺 | `os.Truncate` 截掉 footer | 纯文件操作 |

## 验证

- 写尾：在尾部每个字节位置注入失败，断言必须返回包裹底层错误、且标明失败段落的错误。
- WAL 重写：失败后旧 WAL 必须完整可重放；rename 前崩溃的残留 `.tmp` 不参与重放；成功路径墓碑 op 原样保留（否则被删的 key 会复活）。
- compaction：失败时源文件不得删除、数据仍可读；`MergeSSTable` 与 `CompactSSTable` 两层各测一遍。
- **变异验证**：注入「合并失败仍删源文件」→ 用例立即失败；把元信息加载退回 `go` → 启动契约用例立即失败。一个从未失败过的测试可能什么都没测。
- 崩溃恢复复验：写入 5 万 key → `kill -9` → 重启抽样 516 个 key，**缺失 0**。
