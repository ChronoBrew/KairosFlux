# 内存护栏（Memory Guardrail）基准与验收

> M5 方案 §A.2 的落地文档：组件实现见 `service/guardrail.go`（状态机/采样/告警）、
> `service/guardrail_test.go`（确定性状态机测试）、`service/guardrail_wiring_test.go`
> （v1/v2 Router 接线测试）；错误码裁决（v1 复用 overloaded、v2 新增
> `codec.ErrCodeMemoryLimit=0x1003`）由 M5 协调者确认后落地，理由见下。

## 1. 问题：swap 死亡（动机）

**事故记录（部署现场观察，非本仓库代码缺陷）**：边缘目标机（2 核 3.6G 内存）上
部署的服务进程在数据量爬升期间出现过一次"写入全部超时、进程存活但不可服务"的
事件。事后复盘（top 快照 + 系统日志）确认根因是：进程 RSS 持续爬升越过物理内存
后开始换页（swap），换页后每次写路径的 WAL 落盘与内存拷贝都在 page-in/page-out
上反复摩擦，**服务吞吐塌缩到接近 0，但进程没有任何崩溃/报错信号**——从外部看
就是"卡死"。这类事故与 OOM kill 不同：

| 维度 | OOM kill | swap 死亡 |
| --- | --- | --- |
| 进程状态 | 被内核杀死（有 dmesg 记录） | 活着但性能塌缩（无信号） |
| 可恢复性 | 靠外部重启 | 不人工介入不会恢复 |
| 监控能发现 | 能（进程没了） | 难（进程还在，只有延迟暴涨） |

目标机没有托管环境的内存回收（不留 slack 的容器/memcg 逐出），唯一的防线是
**进程自己在超限前拒收新写入**——这是护栏存在的全部理由：宁可显式拒绝让客户端
重试，也不要在 swap 死亡里越走越远。

## 2. 验收标准（2 核 3.6G 目标机）

### 2.1 功能验收（已由测试覆盖）

- `config.MaxRSSMb`：<=0 关闭护栏（默认 0=不限，显式开启才生效）；>0 时启用。
- RSS 采样：周期 2s，Linux 读 `/proc/self/status` 的 VmRSS（真实驻留集），
  读不到时退回 `runtime.ReadMemStats().Sys` 的保守近似。
- 判定语义：RSS **严格大于** 上限进入 blocked（transition 时打一条 ERROR 告警，
  含 rss_mb/limit_mb）；回落至 **<=90% 上限** 才解除（WARN 一条）。滞回区间内
  既不重复告警、也不放行，防止临界抖动。
- 拒收范围：**只拒写、不拒读**——v1 PUT/DEL 回既有 `overloaded` 状态（客户端
  可识别重试）；v2 写帧（PUT/PUT_VERSIONED/DEL）结构化拒绝
  `ErrCodeMemoryLimit=0x1003`，reason=`memory_limit_reached`（ack=window/none
  连接上该次拒绝计入 received 且 rejected，STAT 对账可见）。GET/SCAN/
  LIST_WRITES 等读路径超限期间照常服务（审计/诊断仍可用）。
- 启动自检：服务启动时打印 `GOGC` 与生效的 `max_rss_mb`（tail 日志可核对
  部署参数；GOGC 决定 Go 堆在 GC 前的放量斜率，是 RSS 爬升的第一变量）。

### 2.2 容量验收（100w 档数据量，占位）

> 100w 档（单前缀约 100 万次写入）的进程 RSS 基线**以发布报告的实测数据为准**
> （发布报告在本里程碑的交付物中，见发布 Agent 的工作区；本文档完成时该数据
> 尚未产出，此处按"基线 + 护栏"两层预算给出验收口径）。

目标机内存 3.6G 的分配口径（验收时按发布报告实测值替换"RSS 基线"占位）：

```
进程 RSS 预算 = RSS 基线（100w 档，发布报告为准） + 护栏余量
护栏余量      = 至少 25% 的基线值（见 §4 生产规模余量说明）
max_rss_mb    = 3.6G * 1024 * 0.8（为系统其它进程/内核页缓存留 20%）
```

验收动作（手动，可在 E2E 环境复现）：

1. 以 `max_rss_mb` 为上限启动服务，灌入 100w 档数据，确认启动自检日志打印
   GOGC 与生效上限。
2. 写入过程中 RSS 不超限时：写入全部成功，护栏零日志输出（稳态不刷）。
3. 人为把 `max_rss_mb` 压到低于当前 RSS（或注入假采样器）时：新写入被拒
   （v1 overloaded / v2 0x1003），读照常，日志出现一条 transition ERROR。
4. RSS 回落到 90% 上限以下后：写入自动恢复（无需重启），日志出现一条 WARN。
5. 护栏拒收期间服务端不 panic、不泄漏（`go test -race` 全绿，见交付报告）。

## 3. 配置与部署

- 配置项：`max_rss_mb`（MiB，int64）。Node 模式读 `config.G.MaxRSSMb`；
  Engine（kairosflux）模式经 `Options.MaxRSSMb` 透传。
- 建议与 GC 参数一起核对：GOGC 越大堆放量越激进，护栏上限应与 GOGC 配合
  校准（启动自检同时打印两者，就是为了部署时一眼核对）。
- 恢复依赖写入侧重试：v1 `overloaded` 与 v2 `0x1003` 都是客户端可识别重试的
  拒绝语义，不是数据丢失——被拒写入未落盘，重试即可。

## 4. 生产规模余量说明

护栏不是内存压缩器，它只是"最后的闸门"。生产规模的余量设计在护栏之上还有
两层：

1. **工作集余量**：单前缀写入历史（版本键）随数据量线性增长，100w 档到更大
   规模（如 ~5000 只标的 × 日线全量）之间，RSS 基线会增长数倍——护栏上限必须
   随发布报告的量级数据滚动校准，**不能在发版后放任自流**（这正是当年 swap
   死亡事故的路径：部署时没有上限，数据量爬升越线无感知）。
2. **护栏余量（至少 25%）**：从"超限拒写"到"进程稳定"需要时间——拒收后已
   在途写入仍会落盘、GC 仍需回收。25% 的缓冲保证拒收发生后进程有足够空间把
   在途工作做完，而不是在边界上继续挣扎。90% 的滞回解除线进一步保证恢复过程
   不抖动。

一句话：护栏的验收口径 = 发布报告实测 RSS 基线 + 25% 护栏余量，且上限
不得超过目标机物理内存的 80%（给系统与页缓存留底）。
